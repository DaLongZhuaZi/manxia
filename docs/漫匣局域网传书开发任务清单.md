## 一、范围基线

第一阶段只做以下目标：

1. APP 内进入页面即可自动开启“局域网传书”服务，同时保留手动停止 / 重启入口。
2. APP 展示局域网访问地址、端口、配对码、当前状态。
3. 浏览器直接访问 APP 本地地址，看到状态页和后续上传入口。
4. APP 端预留文件接收、临时落盘、导入编排接口。
5. 后续上传文件类型复用现有导入链路：
   - 漫画压缩包
   - EPUB / MOBI / AZW3
   - PDF
   - TXT

第一阶段暂不纳入验收：

1. `manxia.top/transfer` 自动扫描局域网设备
2. WebRTC P2P 主链路
3. 公网大文件中继
4. 跨公网、跨 NAT、跨子网传输

### 2.1 2026-05-15 源码核对结果

经源码核对，MVP 主链路已具备对应实现：

1. APP 侧模型、配置、会话、设置键已落地到 `TransferModels.ets`、`TransferConfigManager.ets`、`TransferSessionManager.ets`、`SettingsManager.ets`。
2. 本地 TCP 轻量 HTTP 服务已实现 `GET /`、`GET /api/info`、`GET /api/uploads`、`GET /health`、`POST /api/pair/verify`、`POST /api/upload`。
3. 可选本地 WebSocket 状态通道已实现，用于推送运行态和上传列表，不承担文件数据传输。
4. 上传收件箱、临时落盘、文件名清洗、大小限制、记录清理、删除记录与导入状态回写已落地。
5. `TransferPage.ets` 已支持进入页面自动启动本地服务、自动创建公网房间、顶部卡片前置公网房间码、启动/停止服务、刷新配对码、复制地址/配对码/连接指引、系统分享、二维码、最近上传和继续导入。
6. 设置入口、主导航 `NavDestination`、`https://manxia.top/transfer` App Linking 与 Deep Link 映射已接入。
7. `cloudflare/manxia-worker/` 已实现可部署控制面工程，包含 `/.well-known/applinking.json`、主页、Deep Link 跳转页和 `/transfer` 说明页。

当前未实现但也未纳入 MVP 验收的能力：

1. 跨公网中继、自动局域网发现。
2. 公网房间码目前已能完成信令控制面、局域网地址自动引导和 DataChannel 文件协议 alpha，但正式大文件能力仍需真机验收。
3. 浏览器侧分片续传和更完整的历史面板。

结论：如果以当前 MVP 为范围，不是“只剩 Cloudflare Worker 信令”；MVP 主链路已经基本完成。当前 Worker 信令控制面、浏览器 peer 测试端、APP 自动启动 / 自动建房、Worker 房间码自动验证连接、自动局域网地址引导、Native RTC 真实后端和 DataChannel 文件协议 alpha 都已接入，剩余主要是真机端到端验收、大文件稳定性和二进制 chunk 后端增强。

### 2.2 2026-05-16 Web 组件 WebRTC 方案核对结果

通过用户补充的 HarmonyOS 官方智能文档答复，并结合当前源码与 SDK 声明，后续不需要等待 ArkTS 原生 WebRTC API。可把 WebRTC 运行时放进 `Web` 组件加载的受控 HTML 页面中，由页面使用标准 JavaScript `RTCPeerConnection` / `RTCDataChannel`；ArkTS 通过 `javaScriptProxy`、`WebMessagePort` 或 `runJavaScript` 与页面交换状态和文件片段。

当前判断：

1. 不是“只剩 Cloudflare Worker 端信令设计尚未实现”。
2. Worker Durable Object 信令、APP Host 信令客户端、浏览器 peer 信令面板都已经具备基础实现。
3. 真正剩余的是 WebRTC 数据通道和文件数据面的落地：
   - APP 侧 Web 组件宿主页。
   - 浏览器 `/transfer` WebRTC peer 发送端。
   - SDP / ICE 与现有 Worker 信令消息的双向桥接。
   - DataChannel 文件分片协议。
   - JS 到 ArkTS 的分片落盘桥接。
   - 大文件背压、失败清理、导入回写和局域网直连回退。

权限策略：

1. DataChannel 本身不需要摄像头 / 麦克风。
2. 当前不默认新增 `CAMERA` / `MICROPHONE` 权限，避免扩大权限面。
3. 如 Web 组件收到音视频权限请求，默认拒绝；只有未来明确引入音视频能力时再单独申请。

### 2.3 2026-05-16 Native RTC 路线落地进度

在继续分析 JSVM / 纯 JS 与 C/C++ 原生路线后，当前工程结论已调整为：

1. **不使用 JSVM / 纯 JS 补 WebRTC 数据通道**。JSVM 不是浏览器运行时，也不是 Node.js 运行时，不能凭空提供 `RTCPeerConnection`、`RTCDataChannel`、ICE、DTLS、SCTP 等协议栈。
2. **信令继续留在 ArkTS + Worker**。现有 `TransferSignalClientService.ets` 和 Worker Durable Object 已能处理房间、WebSocket、`offer / answer / candidate / ping` 转发，不需要把信令强行下沉到 Native。
3. **Native 只负责数据面**。C/C++ 层已接入 `libdatachannel`，提供 PeerConnection / DataChannel / SDP / ICE 操作；ArkTS 负责页面状态、房间创建、信令转发、收件箱落盘和导入编排。
4. **本轮已落地 Native RTC 真实后端**：
   - 新增 `entry/src/main/cpp/transfer_rtc/transfer_rtc_native.cpp`。
   - 新增 `entry/src/main/cpp/transfer_rtc/CMakeLists.txt` 并接入根 Native CMake。
   - 新增 `libtransfer_rtc_native.so` 类型包并接入 `entry/oh-package.json5`。
   - 新增 `TransferNativeRtcService.ets`、Native RTC 运行态模型和传书页“Native RTC 数据通道”状态卡。
   - 已交叉编译并接入 `libdatachannel` 与 RTC 专用 mbedTLS 运行库。
5. **当前真实状态**：Native RTC 外壳已经切到真实 `libdatachannel` 后端，APP 完整 `assembleHap` 构建通过；DataChannel 文件协议 alpha 已通过 JSON + Base64 文本分片接入收件箱，后续重点是真机端到端验收、50MB 级大文件稳定性和 Native 二进制 chunk 能力。

## 四、工程拆解

### T1 基础模型与设置项

目标：

1. 为配置、会话、运行态、HTTP 信息响应建立明确类型。

建议设置项：

1. `LAN_TRANSFER_PORT`
2. `LAN_TRANSFER_AUTO_STOP_MINUTES`
3. `LAN_TRANSFER_MAX_FILE_SIZE_MB`
4. `LAN_TRANSFER_ALLOW_BACKGROUND_TRANSFER`
5. `LAN_TRANSFER_WS_ENABLED`

验收标准：

1. 新增类型文件不依赖 `any` / `unknown`
2. 默认值可直接被页面与服务层消费

目标：

1. 将设置系统与传书功能隔离，避免页面直接读写零散 key。

验收标准：

1. 页面和服务层都通过 Manager 访问配置
2. 会话可刷新、可过期、可清空

### T3 本地服务骨架

目标：

1. 使用 HarmonyOS 已确认可用的 TCP Server 能力启动本地监听。
2. 先实现“浏览器能打开状态页”和“浏览器能拉到 JSON 状态”。

接口范围：

1. `GET /`
2. `GET /api/info`
3. `GET /health`

验收标准：

1. 服务可启动/停止
2. 页面能拿到运行态快照
3. 浏览器访问本地地址时能收到文本页面
4. `/api/info` 可返回结构化 JSON

### T4 页面与导航接入

目标：

1. 让用户能从设置页进入“局域网传书”页面。
2. 页面展示服务状态、地址、配对码、配置摘要。

验收标准：

1. 设置页出现入口
2. 导航路由生效
3. 页面可以启动/停止服务并刷新状态

### T5 上传协议与落盘

目标：

1. 支持浏览器上传本地文件到 APP 临时目录。
2. 限制大小、校验扩展名、返回结果对象。

当前已实现接口：

1. `POST /api/upload`
2. `POST /api/pair/verify`

1. 上传文件可写入沙箱临时目录

1. 将上传结果路由到现有导入链路，而不是重新造一套导入系统。

优先复用：

1. `DownloadSyncPage.ets`

3. `PdfImportService.ets`
4. 现有电子书解析/导入逻辑

验收标准：

1. 漫画压缩包、电子书、PDF、TXT 至少各有一条明确编排路径
2. 上传记录可由传书页转交给 `DataManagementPage`

1. 传书记录会在导入成功、失败、取消后回写状态。
2. 浏览器上传页已显示基础上传进度。

4. 传书页已支持复制主地址、复制配对码、复制完整连接指引，以及系统分享连接指引。

### T11 Native RTC DataChannel PoC

目标：

6. 失败时明确提示继续使用局域网直连。

### T12 DataChannel 文件协议与导入闭环

目标：

1. 定义 `mx-transfer-file/0.1` DataChannel 文件协议。
2. 支持 `file_start`、`file_chunk`、`file_end`、`ack`、`error`。
3. 浏览器发送端使用 `RTCDataChannel.bufferedAmount` 做背压控制。
4. APP 端桥接服务按片写盘，并复用收件箱和继续导入流程。
5. 覆盖 50MB 以上文件的中断、失败清理和导入回写。

当前已完成：

1. `TransferModels.ets` 已定义 `mx-transfer-file/0.1` 消息模型、ACK / error 构造和解析函数。
2. `TransferRtcFileReceiverService.ets` 已实现 APP 端接收状态机：`file_start` 创建收件箱临时写盘会话，`file_chunk` Base64 解码后追加写入，`file_end` 完成落盘并生成收件箱记录。
3. `TransferPage.ets` 已在 Native RTC 事件轮询中处理 DataChannel 文件消息、发送 ACK / error，并在 UI 显示文件接收状态与进度。
4. Worker `/transfer` 页面已新增 RTC 文件选择和发送区，支持多文件顺序发送、`bufferedAmount` 背压、逐片 ACK 等待、失败提示和完成提示。
5. 当前受限于 Native NAPI 暂只暴露 `sendText` / 文本事件，文件片段 alpha 使用 JSON + Base64 文本承载；后续应把 `file_chunk` 升级为真正二进制 `ArrayBuffer` / native binary message。

验收标准：

1. 50MB 文件可完成传输、落盘和继续导入。
2. 传输中断后临时文件可清理。
3. 不支持后缀、超大小、重复文件名等规则沿用现有上传收件箱限制。
4. P2P 不通时不阻塞局域网直连主链路。

## 六、开发顺序建议

1. 先完成 T1-T4，形成“能开服务、能看页面、能访问本地状态页”的开发基座。
2. 再做 T5，把浏览器上传打通到沙箱临时目录。
3. 最后做 T6，把上传结果接到现有导入体系。

这样推进的原因是：

1. 能尽快验证 HarmonyOS 本地服务端方案是否稳定。
2. 能把风险前置在网络服务和生命周期管理，而不是先陷入文件解析细节。
3. 后续上传协议和导入编排都能建立在已验证的服务基础上继续扩展。
