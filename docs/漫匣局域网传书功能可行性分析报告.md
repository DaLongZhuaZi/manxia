# 漫匣局域网传书功能可行性分析与实施建议（修订版）

> 文档目的：将“局域网传书”从概念性设想收敛为可指导后续开发的实现方案  
> 修订时间：2026-05-14  
> 评估基线：`HarmonyOS Next API 23`、当前仓库代码、当前 `manxia.top` Cloudflare Worker 现状、现代浏览器本地网络访问限制  
> 结论摘要：**功能可做，但原报告中的 WebRTC 主路径与“访问 manxia.top 后自动发现局域网设备”不适合作为当前开发主线。推荐改为“APP 本地服务 + 局域网直连 + 手动地址/二维码辅助”的落地方案。**

---

## 一、执行结论

### 1.1 最终结论

“局域网传书”对漫匣来说**具备真实可行性**，但必须调整目标和架构：

1. **可行的部分**
   - APP 在局域网内开启本地传输服务。
   - 浏览器通过局域网地址直接访问 APP。
   - 浏览器上传漫画压缩包、电子书、PDF、TXT 到 APP。
   - APP 复用现有导入链路完成落盘、分类、导入、进度展示。
   - APP 在后台保持一段时间的数据传输能力。

2. **当前不应作为主线承诺的部分**
   - 用户访问 `https://manxia.top/transfer` 后，网页**自动扫描并发现**局域网内的漫匣设备。
   - 在当前仓库和当前本机 SDK 基线下，将 **WebRTC** 作为第一阶段主传输方案。
   - 让现有 Cloudflare Worker 直接承担局域网设备发现或大文件中继传输。

3. **推荐主方案**
   - 第一阶段采用：**APP 本地 HTTP 服务 + 可选本地 WebSocket 状态通道 + 手动地址/二维码辅助连接**
   - `manxia.top` 在第一阶段只承担：**深链拉起、说明页、帮助页、后续入口页**，**不承担数据平面**

### 1.2 对原报告结论的修正

原报告的“**完全可行**”需要改为：

> **需求可行，但原技术路线不完整，且部分关键假设与当前仓库和当前 HarmonyOS SDK 实际情况不一致。应改为分阶段实施，并以局域网本地直连方案为 MVP。**

## 二、评估依据

本次修订不是空想设计，结论基于以下四类事实：

### 2.1 仓库现状

当前仓库中已经存在以下与“传书”直接相关的可复用基础：

1. **现有导入能力已较完整**
   - `entry/src/main/ets/pages/DownloadSyncPage.ets`
   - 该页面已经识别并导入：
     - 漫画压缩包：`zip/cbz/rar/cbr/7z/tar/gz/tgz/bz2/xz/lzma`
     - 电子书：`epub/mobi/azw/azw3`
     - `pdf`
     - `txt`

2. **现有网络扫描能力已存在，但用途不是浏览器传书**
   - `entry/src/main/ets/Framework/Network/NetworkScannerAdapter.ets`
   - `entry/src/main/ets/pages/NetworkFolderPage.ets`
   - 当前实现针对的是 `WebDAV / FTP / FTPS / SFTP / SMB` 这类网络文件夹接入与扫描，不等于已有“网页对 APP 传书”的服务端能力。

3. **现有后台长时任务基础已存在**
   - `entry/src/main/module.json5`
   - `entry/src/main/ets/Framework/Task/BackgroundTaskHelper.ets`
   - 仓库已声明并实际使用 `dataTransfer` 背景模式，也已申请：
     - `ohos.permission.INTERNET`
     - `ohos.permission.GET_NETWORK_INFO`
     - `ohos.permission.KEEP_BACKGROUND_RUNNING`

4. **现有 Cloudflare Worker 已有控制面工程骨架**
   - `docs/cloudflare-worker.md`
   - `cloudflare/manxia-worker/`
   - `entry/src/main/module.json5`
   - 当前仓库已补上 Worker 工程骨架、`wrangler` 配置和 `/transfer` 控制面入口。
   - 但它仍然只承担 App Linking、深链落地页和传书帮助入口，不承担局域网发现、信令协调或上传中继。

### 2.2 本机 HarmonyOS SDK 实际能力

按 `AGENTS.md` 规则，本次优先核对了本机 SDK：

- `F:\HarmonyOS\SDK\23\ets\api\@ohos.net.socket.d.ts`
- `F:\HarmonyOS\SDK\23\ets\api\@ohos.net.webSocket.d.ts`
- `F:\HarmonyOS\SDK\23\ets\api\@ohos.net.http.d.ts`
- `F:\HarmonyOS\SDK\23\ets\api\@ohos.backgroundTaskManager.d.ts`

核对结果：

1. **存在本地 TCP 服务端能力**
   - `constructTCPSocketServerInstance()`
   - `TCPSocketServer.listen(...)`

2. **存在本地 WebSocket 服务端能力**
   - `createWebSocketServer()`
   - `WebSocketServer.start(...)`
   - `WebSocketServer.on('messageReceive', ...)`

3. **存在 HTTP 客户端能力**
   - `createHttp()`
   - 但 SDK 没有提供同级别的现成 ArkTS HTTP Server 封装，需要基于 Socket 自行实现轻量 HTTP 服务。

4. **存在后台长任务能力**
   - `startBackgroundRunning(...)`
   - 可用于 `dataTransfer` 场景。

5. **未在当前 SDK API 声明中检索到可直接采用的原生 WebRTC 能力**
   - 未检索到 `WebRTCKit`
   - 未检索到 `RTCPeerConnection`
   - 未检索到 `RTCDataChannel`

因此，在当前项目基线下：

> **“本地 TCP / WebSocket 服务”是 SDK 已确认能力；“原生 WebRTC 主链路”不是当前阶段可以直接当成已确认能力使用的前提。**

### 2.3 浏览器现实约束

现代浏览器对“公网 HTTPS 页面访问局域网本地服务”的限制明显强于旧时代设想，主要问题包括：

1. **Mixed Content**
   - `https://manxia.top` 页面直接访问 `http://192.168.x.x:port` 并不可靠。

2. **Private Network Access / Local Network Access**
   - 浏览器对从公网页面访问本地网段资源的限制越来越严格。
   - 即使部分版本可弹权限提示，也不应把它当作产品级稳定方案。

3. **WebSocket 也受安全上下文影响**
   - `https://` 页面连接 `ws://` 本地服务存在兼容性和策略风险。
   - 若改成 `wss://`，本地服务端证书管理复杂度会大幅上升。

因此：

> **“在 manxia.top 页面里扫描 192.168.x.x 并直连本地 HTTP / ws 服务”不适合作为 MVP 主方案。**

### 2.4 Cloudflare Worker 现实边界

Cloudflare Worker 可以做：

1. 深链落地页
2. App Linking 验证文件
3. 说明页面
4. 小规模控制面能力
   - 房间信息
   - 一次性令牌
   - 信令协调

Cloudflare Worker 不适合直接承担：

1. 局域网设备扫描
2. 直接访问用户局域网
3. 第一阶段的大文件中继主链路

另外，原报告中把 WebSocket 连接写进 KV 的伪代码不成立。WebSocket 会话应由 Durable Object 或服务端内存持有，不能按普通键值对象存储处理。

## 三、问题重新定义

为了让文档真正支撑开发，必须先把“需求说清楚”。

### 3.1 我们真正要解决的核心问题

对当前漫匣来说，“局域网传书”更准确的 MVP 目标应该是：

> 用户在漫匣 APP 中开启传书服务后，能在同一局域网内通过浏览器把漫画压缩包、电子书、PDF、TXT 文件传到 APP，并由 APP 自动导入。

### 3.2 第一阶段不追求的目标

以下目标不建议纳入第一阶段验收：

1. 访问 `manxia.top/transfer` 后自动发现本地设备
2. 完全零输入、零确认、零配对
3. 基于公网 Worker 的大文件转发
4. WebRTC P2P
5. 跨子网、跨 NAT、跨公网传书

### 3.3 第一阶段允许的用户动作

以下动作在 MVP 中是可接受的：

1. 在 APP 内手动开启“局域网传书”
2. 查看并复制本地地址
3. 在浏览器手动输入本地地址
4. 输入 6 位配对码
5. 在 APP 端确认接收

只要交互清晰，这些动作是远比“假自动化但不稳定”更合适的产品取舍。

## 四、真实可行性评估

### 4.1 按模块评估

| 模块 | 结论 | 可行性 | 说明 |
|------|------|--------|------|
| APP 接收文件后的导入链路 | 可直接复用 | 高 | 已有 Download 同步与导入基础 |
| APP 局域网地址探测 | 可复用部分能力 | 高 | 已有网络信息和局域网扫描基础 |
| APP 后台保活与数据传输场景 | 已有基础 | 中高 | 已有 `dataTransfer` 与 `KEEP_BACKGROUND_RUNNING` |
| APP 本地 TCP 服务端 | 可开发 | 高 | SDK 已确认支持 |
| APP 本地 WebSocket 服务端 | 可开发 | 高 | SDK 已确认支持 |
| APP 原生 WebRTC | 当前不建议主用 | 低 | 当前 SDK/仓库未见可直接落地依据 |
| 浏览器上传到局域网 APP | 可开发 | 中高 | 前提是浏览器直接访问局域网地址 |
| 浏览器从 `manxia.top` 自动扫局域网 | 不建议主用 | 低 | 浏览器安全策略风险高 |
| Cloudflare Worker 做深链和说明入口 | 已具备基础 | 高 | 当前已有 deep link 文档、Worker 工程骨架与 `/transfer` 控制面入口 |
| Cloudflare Worker 做局域网发现 | 不成立 | 低 | Worker 无法访问用户局域网 |
| Cloudflare Worker 做大文件中继主链路 | 不建议 | 低中 | 成本、复杂度、稳定性均不适合第一阶段 |

### 4.2 总体评估

如果把目标改成：

> “APP 开本地服务，浏览器直连 APP 局域网地址上传文件，APP 自动导入”

那么项目是**明确可做**的。

如果坚持目标不变：

> “用户只访问 `manxia.top/transfer`，网页自动扫描局域网并连上漫匣”

那么项目会卡在浏览器安全策略和连接稳定性上，难以成为可靠产品。

## 五、推荐架构

## 5.1 第一阶段推荐架构：局域网本地直连

### 架构说明

第一阶段推荐使用：

**APP 本地 HTTP 服务 + 可选本地 WebSocket 状态通道 + 手动地址 / 二维码辅助**

```text
┌─────────────────────────────────────────────┐
│                 漫匣 APP                    │
│                                             │
│  1. 开启局域网传书                           │
│  2. 启动本地服务                             │
│     - HTTP: 提供上传页面与上传接口           │
│     - WS:   提供进度与状态推送（可选）       │
│  3. 显示本地地址、端口、配对码、二维码        │
│  4. 接收文件后复用现有导入链路               │
└─────────────────────────────────────────────┘
                    ▲
                    │ 局域网直连
                    │
┌─────────────────────────────────────────────┐
│                浏览器（PC/Pad）              │
│                                             │
│  1. 输入/打开 APP 显示的本地地址             │
│  2. 输入配对码                               │
│  3. 选择文件上传                             │
│  4. 查看传输进度                             │
└─────────────────────────────────────────────┘
```

### 关键原则

1. **数据平面走局域网，不走 Cloudflare**
2. **页面入口优先走本地地址，不走 manxia.top 代理**
3. **控制面可以很轻，传输面必须稳定**
4. **先做能稳定收书，再谈自动发现**

## 5.2 `manxia.top` 在第一阶段的定位

第一阶段建议把 `manxia.top` 定位为：

1. 深链拉起入口
2. 帮助说明页
3. 传书功能介绍页
4. 后续版本升级入口

不建议把 `manxia.top` 第一阶段定位为：

1. 局域网发现器
2. 文件上传中继
3. WebRTC 信令核心

### 推荐表现形式

`https://manxia.top/transfer` 可以做成：

1. 介绍如何在 APP 内开启传书
2. 提供“打开漫匣”按钮
3. 展示三种连接方式：
   - 手动输入局域网地址
   - 查看 APP 显示的二维码
   - 复制本地地址到浏览器打开

它是**入口和说明页**，不是第一阶段实际数据通道。

## 六、推荐实现方案

## 6.1 APP 侧职责拆分

建议沿用当前仓库既有模式，按 `pages / managers / services` 拆分：

### 页面层

新增：

1. `TransferPage.ets`
   - 开启/关闭服务
   - 显示地址、端口、配对码、二维码
   - 显示已连接客户端和上传队列
   - 提供停止服务入口

### 服务层

建议新增：

1. `LocalTransferServerService.ets`
   - 统一管理 HTTP 服务生命周期
   - 统一管理可选 WebSocket 服务生命周期

2. `TransferSessionManager.ets`
   - 管理配对码、令牌、会话过期
   - 管理客户端状态

3. `TransferImportService.ets`
   - 将上传文件落到临时目录
   - 调用现有导入链路
   - 回传导入状态

### 管理器层

建议新增：

1. `TransferConfigManager.ets`
   - 端口
   - 自动关闭时间
   - 单文件大小限制
   - 是否允许后台继续传输

2. `TransferLogManager.ets`
   - 使用现有 `Logger.ets`
   - 记录服务启动、连接、配对、上传、导入、失败信息

## 6.2 传输协议建议

### 不建议第一阶段采用

1. 浏览器 `multipart/form-data` 直传大文件
   - 服务端自行解析 multipart 成本高

2. WebRTC DataChannel
   - 当前 SDK 能力不确定

### 建议第一阶段采用

1. **轻量本地 HTTP 页面**
   - `GET /` 返回上传页面
   - 页面由 APP 本地服务直接提供

2. **JSON 控制接口**
   - `POST /api/pair`
   - `POST /api/upload/init`
   - `POST /api/upload/finish`
   - `GET /api/upload/status`

3. **原始二进制分片上传**
   - `PUT /api/upload/chunk?uploadId=xxx&index=1`
   - 请求体直接放二进制
   - 避免解析复杂 multipart

4. **可选本地 WebSocket**
   - 只用于推送进度和状态
   - 不承担文件主传输

## 6.3 建议接口草案

### 1. 获取基础信息

`GET /api/info`

返回：

```json
{
  "appName": "漫匣",
  "version": "1.0",
  "deviceName": "HUAWEI Phone",
  "pairRequired": true,
  "maxFileSizeBytes": 2147483648,
  "supportedExtensions": [
    "zip", "cbz", "rar", "cbr", "7z",
    "epub", "mobi", "azw", "azw3",
    "pdf", "txt"
  ]
}
```

### 2. 配对

`POST /api/pair`

请求：

```json
{
  "code": "123456",
  "clientName": "Chrome on Windows"
}
```

返回：

```json
{
  "success": true,
  "token": "temporary-session-token",
  "expiresInSeconds": 600
}
```

### 3. 初始化上传

`POST /api/upload/init`

请求：

```json
{
  "token": "temporary-session-token",
  "fileName": "example.epub",
  "fileSize": 12345678,
  "mimeType": "application/epub+zip",
  "chunkSize": 262144,
  "totalChunks": 48
}
```

返回：

```json
{
  "success": true,
  "uploadId": "upload_abc123"
}
```

### 4. 上传分片

`PUT /api/upload/chunk?uploadId=upload_abc123&index=0&token=temporary-session-token`

- 请求体：二进制数据
- 返回：简单 JSON 确认

### 5. 完成上传

`POST /api/upload/finish`

请求：

```json
{
  "token": "temporary-session-token",
  "uploadId": "upload_abc123"
}
```

返回：

```json
{
  "success": true,
  "queued": true,
  "importTaskId": "import_task_001"
}
```

### 6. 查询状态

`GET /api/upload/status?token=temporary-session-token&taskId=import_task_001`

返回：

```json
{
  "status": "importing",
  "progress": 72,
  "message": "正在导入电子书"
}
```

## 七、安全设计建议

第一阶段安全目标不是“零信任企业级”，而是“局域网可用且不会裸奔”。

## 7.1 必做项

1. 服务默认关闭
2. 用户手动开启服务
3. 使用 6 位或 8 位一次性配对码
4. 配对成功后发放短期 token
5. token 过期自动失效
6. 服务空闲自动关闭
7. 限制可上传后缀和 MIME 类型
8. 限制单文件大小和总会话大小
9. 文件名做清洗，禁止路径穿越
10. 记录关键操作日志

## 7.2 建议项

1. 首次连接时在 APP 上显示客户端名称和 IP
2. 可选“需要点击确认才接收”
3. 绑定同一局域网会话
4. 同时上传连接数限制
5. 导入失败后保留错误原因和清理策略

## 7.3 不建议第一阶段做的复杂项

1. 自建 TLS 证书本地 `https/wss`
2. 端到端自定义加密层
3. 基于 Cloudflare 的公网 relay 加密隧道

## 九、为什么不推荐把 WebRTC 作为当前主方案

原报告最大的问题不是“WebRTC 完全不可能”，而是**把它放错了阶段**。

### 9.1 当前不推荐的原因

1. 当前本机 SDK 与仓库里没有现成 WebRTC 落地依据
2. 第一阶段真正的需求是“稳定收书”，不是“炫技式 P2P”
3. 即使 WebRTC 成立，浏览器入口、信令、回退、失败处理仍然复杂
4. 大文件传输时，产品首要问题是稳定与可恢复，而不是协议先进性

### 9.2 WebRTC 适合放到什么阶段

只有在下面条件满足后，才建议重新评估：

1. HarmonyOS 侧原生 WebRTC 能力已明确可用
2. 我们已完成局域网本地直连 MVP
3. 我们确认产品真的需要“无需输入本地地址”的增强体验
4. 我们接受显著更高的联调与维护成本

---

## 十、为什么不推荐“网页自动扫描局域网设备”

这是最容易在立项阶段误判、开发阶段卡死、上线阶段不稳定的部分。

### 10.1 不推荐原因

1. 浏览器安全策略不稳定
2. HTTPS 页面对本地 HTTP / ws 访问受限
3. 扫描整个网段会带来性能、权限、误报、用户认知问题
4. 不同浏览器、不同平台、不同版本行为可能不一致

### 10.2 结论

> “自动发现”只能作为后续增强方向，不能作为当前版本的基础前提。

如果后续确实需要增强体验，优先顺序应为：

1. APP 直接展示本地地址
2. APP 生成二维码
3. 研究是否支持局域网服务名
4. 最后才考虑网页自动发现

## 十二、建议的验收标准

## 12.1 功能验收

必须满足：

1. APP 开启服务后能显示局域网地址
2. 浏览器访问本地地址能看到上传页面
3. 配对成功后可上传文件
4. 上传完成后 APP 自动导入
5. 支持以下文件类型：
   - 漫画压缩包
   - 电子书
   - PDF
   - TXT
6. APP 关闭服务后地址失效

## 12.2 稳定性验收

建议至少覆盖：

1. 10MB 文件
2. 100MB 文件
3. 500MB 文件
4. Wi-Fi 稳定场景
5. 浏览器刷新场景
6. APP 切后台场景
7. 传输中断场景

## 12.3 安全验收

必须满足：

1. 未配对不能上传
2. token 过期后不能继续上传
3. 非支持文件类型拒绝导入
4. 文件名不能造成路径穿越
5. 服务关闭后不再接受连接

---

## 十三、后续开发建议

为了减少返工，建议按下面顺序推进：

1. **先做技术验证**
   - 验证本地 HTTP 服务最小可用实现
   - 验证浏览器访问本地地址是否稳定
   - 验证上传后接入现有导入链路

2. **再做正式页面**
   - 传书设置项
   - 传书主页
   - 上传状态页

3. **最后再考虑 Cloudflare 入口页**
   - 不要一开始就做公网入口与信令体系

---

## 十四、最终建议

### 14.1 立项建议

建议正式按以下版本目标立项：

> **漫匣局域网传书 MVP：APP 开启本地传输服务，浏览器通过局域网地址直连 APP 上传文件，APP 自动导入。**

### 14.2 不建议立项时写进承诺的内容

以下内容不要写进第一阶段对外承诺：

1. 自动扫描局域网设备
2. WebRTC P2P
3. 访问 `manxia.top` 即自动连上 APP
4. 跨公网传书

### 14.3 推荐路线总结

**当前最靠谱、最贴合你们仓库现状、最能支撑后续开发工作的路线是：**

1. 复用现有导入链路
2. 新增本地轻量服务端
3. 浏览器直连局域网地址
4. 用配对码与短期 token 保证基本安全
5. `manxia.top` 只做入口与说明，不做第一阶段数据通道
