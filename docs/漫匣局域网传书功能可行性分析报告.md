# 漫匣局域网传书功能可行性分析与实施建议（修订版）

> 文档目的：将“局域网传书”从概念性设想收敛为可指导后续开发的实现方案
>
> 修订时间：2026-05-16
>
> 评估基线：`HarmonyOS Next API 23`、当前仓库代码、当前 `manxia.top` Cloudflare Worker 现状、现代浏览器本地网络访问限制  
>
> 结论摘要：**局域网直连 MVP 已基本落地；WebRTC 不建议回到第一阶段主链路。高级阶段当前已完成 Worker 信令控制面部署、APP 自动启动本地服务与自动创建公网房间、浏览器 peer 房间码自动验证连接、公网房间到局域网直连页的自动跳转引导、Native RTC libdatachannel 后端接入，以及 DataChannel 文件协议 alpha；剩余重点是真机端到端验收、50MB 级大文件稳定性、二进制 chunk 和复杂网络回退。**

## 一、执行结论

### 1.1 最终结论

“局域网传书”对漫匣来说**具备真实可行性**，但必须调整目标和架构：

1. **可行的部分**
   - APP 在局域网内开启本地传输服务。
   - 浏览器通过局域网地址直接访问 APP。
   - 浏览器上传漫画压缩包、电子书、PDF、TXT 到 APP。
   - APP 复用现有导入链路完成落盘、分类、导入、进度展示。
   - APP 在后台保持一段时间的数据传输能力。

2. **当前不应作为主线承诺的部分**
   - 用户访问 `https://manxia.top/transfer` 后，网页**自动扫描并发现**局域网内的漫匣设备。
   - 在当前仓库和当前本机 SDK 基线下，将 **WebRTC** 作为第一阶段主传输方案。
   - 让现有 Cloudflare Worker 直接承担局域网设备发现或大文件中继传输。

3. **推荐主方案**
   - 第一阶段采用：**APP 本地 HTTP 服务 + 可选本地 WebSocket 状态通道 + 手动地址/二维码辅助连接**
   - `manxia.top` 在第一阶段只承担：**深链拉起、说明页、帮助页、后续入口页**，**不承担数据平面**
   - 高级阶段优先采用：**Native C/C++ 承载 DataChannel 协议栈，ArkTS / Worker 继续负责房间、信令转发、状态展示、落盘与导入编排**
   - Web 组件 WebRTC 方案保留为备用路线，用于 ArkWeb 真机兼容性满足且桥接成本可控的场景

### 1.2 对原报告结论的修正

原报告的“**完全可行**”需要改为：

> **需求可行，但原技术路线不完整，且部分关键假设与当前仓库和当前 HarmonyOS SDK 实际情况不一致。应改为分阶段实施，并以局域网本地直连方案为 MVP。**

### 1.3 2026-05-15 当前实现进度核对

结合当前源码，第一阶段“APP 本地服务 + 局域网直连 + 手动地址 / 二维码辅助连接”的 MVP 主链路已经基本落地：本地 TCP HTTP 服务、可选本地 WebSocket 状态通道、配对码与 token、上传落盘、收件箱、继续导入、导入结果回写、设置入口、传书页、二维码与连接分享、`manxia.top/transfer` 控制面说明页均已有实现。

高级连接能力已经进入实现阶段：Cloudflare Worker 已新增并部署房间码、Durable Object WebSocket 中继和基础信令转发；APP 侧已新增 Worker 信令客户端服务并接入传书页，且进入页面会自动启动本地服务、自动创建公网房间，并把公网房间码前置到顶部局域网传书卡片；浏览器 `/transfer` 页面已升级为 peer RTC 测试端，输入或粘贴 8 位房间码后会自动验证并连接；房间连接成功后，APP 已能通过 `lan_url` 控制消息自动下发局域网地址和配对码，Worker 网页端会倒计时跳转到 APP 本地服务；Native RTC 已完成 `libdatachannel` 后端替换；DataChannel 文件协议 alpha 已能从浏览器按片发送并写入 APP 收件箱。尚未完成的是跨设备真机端到端验收、50MB 级大文件稳定性、二进制 chunk、中继传输和自动发现。它们不属于当前 MVP 的剩余验收项。

### 1.4 2026-05-16 Web 组件 WebRTC DataChannel 可行性补充

用户已通过 HarmonyOS 官方智能文档确认：当前不必等待 ArkTS 原生 WebRTC Kit，可以通过 `Web` 组件嵌入 WebRTC 页面，在页面内使用标准 JavaScript `RTCPeerConnection` / `RTCDataChannel` 完成 P2P 数据通道，再通过 ArkTS 与 JavaScript 桥接把文件片段交给 APP。

结合本仓库源码与本机 SDK 声明，这条路线**具备落地价值**，但它改变的是 WebRTC 的承载边界，而不是减少所有剩余工作：

1. **可行点**
   - APP 侧已有 `TransferSignalClientService.ets`，可以创建 Worker 房间、连接 Host WebSocket、发送 `offer / answer / candidate / ping` 等信令消息。
   - Worker 侧 `TransferSignalRoom` Durable Object 已能按房间持有 WebSocket，会转发 `offer / answer / candidate / bye / ping` 控制消息。
   - 浏览器 `/transfer` 页面已能以 `peer` 身份连接信令房间，为后续补 WebRTC 发送端提供入口。
   - HarmonyOS `Web` 组件与 `WebviewController` 在 SDK 声明中具备 `javaScriptProxy` / `registerJavaScriptProxy`、`runJavaScript`、`WebMessagePort` 等 ArkTS 与 JS 通信能力。
   - `TransferUploadStoreService.ets` 已经能分段写入临时文件、完成收件箱记录和导入结果回写，可被 WebRTC 接收链路复用。

2. **关键风险**
   - 需要真机验证 ArkWeb 在目标 API / 目标设备上对 `RTCPeerConnection`、`RTCDataChannel` 的实际可用性。
   - 需要验证本地 `$rawfile(...)` 页面是否满足 WebRTC 所需安全上下文；若不满足，应改为加载 `https://manxia.top/transfer-host` 这类受控 HTTPS 页面，并用 `javaScriptProxy.permission` 限定可信域名。
   - 大文件不能一次性从 JS 传给 ArkTS。必须分片、限流、校验、落盘，并处理 `RTCDataChannel.bufferedAmount` 与 ArkTS 写盘背压。
   - `javaScriptProxy` 更适合控制消息和小块数据；生产链路应优先评估 `WebMessagePort` 传递 `ArrayBuffer`，不行再回退到小块 Base64 文本。
   - DataChannel 能穿透多少 NAT 取决于 STUN/TURN。没有 TURN 时，复杂网络下 P2P 失败是正常情况，必须保留局域网 HTTP 直连作为主回退。

3. **结论**
   - 这条路线可以作为 Phase 3 的实际实施方案。
   - 它不推翻已完成的局域网直连 MVP。
   - 当前不应再说“只剩 Cloudflare Worker 端信令设计尚未实现”。更准确地说：**Worker 信令骨架已经实现；剩余是 Web 组件 WebRTC 宿主页、浏览器发送端、ArkTS-JS 文件桥接、DataChannel 文件协议、兼容性验证与失败回退。**

### 1.5 2026-05-16 Native RTC 路线补充与当前落地状态

继续核对 JSVM / 纯 JS / C 原生路线后，当前更稳妥的高级阶段路线调整为：

1. **JSVM / 纯 JS 不适合作为 WebRTC 补齐方案**
   - JSVM 只能运行 JS 逻辑，不内置浏览器 Web API，也不内置 Node.js 网络模块。
   - `RTCPeerConnection` / `RTCDataChannel` 背后需要 ICE、DTLS、SCTP、拥塞控制等协议栈，不可能只靠普通 JS 补齐。
   - 因此 JSVM 只适合脚本执行、协议编排或格式处理，不适合作为 WebRTC 数据通道实现。

2. **C/C++ 原生模块适合作为数据面补齐方案**
   - HarmonyOS Native 工程已存在 NAPI 模块体系，当前仓库已有 `jsvm_engine`、`quickjs`、`webdav_native`、`avif_decoder` 等 Native 模块。
   - 当前已接入 `libdatachannel`，以较轻量的 C/C++ WebRTC DataChannel 栈实现 PeerConnection、SDP、ICE 和 DataChannel。
   - 当前已通过信令 `lan_url` 和 DataChannel 文本补发两条路径实现“公网房间连接后自动打开局域网直连页”的引导闭环。
   - Google libwebrtc 体积、编译链和维护成本明显更高，不作为第一选择。

3. **信令不下沉到 Native**
   - 现有 `TransferSignalClientService.ets` 与 Worker Durable Object 已能创建房间、连接 WebSocket 并转发 `offer / answer / candidate / ping`。
   - Native 只暴露 `createPeer / createOffer / setRemoteDescription / addIceCandidate / sendText` 等数据面接口。
   - ArkTS 继续负责编排 Worker 信令和 Native Peer 生命周期。

4. **本轮已落地 Native RTC 真实后端**
   - 新增 `entry/src/main/cpp/transfer_rtc/transfer_rtc_native.cpp` 与 CMake 接入。
   - 新增 `libtransfer_rtc_native.so` 类型包。
   - 新增 `TransferNativeRtcService.ets` 与 `TransferNativeRtcRuntime` / `TransferNativeRtcCapabilities` 模型。
   - `TransferPage.ets` 公网页签已新增“Native RTC 数据通道”状态卡，可检测 Native 模块和尝试创建 Host Peer。
   - 已交叉编译并接入 `libdatachannel` 与 RTC 专用 mbedTLS 运行库，完整 `assembleHap` 构建已通过。

5. **当前真实能力边界**
   - 当前 Native 后端代码已切到 `libdatachannel`，不再是纯 `stub`。
   - 构建链路已验证，真机运行时仍需确认 `backend=libdatachannel`、`dataChannelSupported=true`。
   - Worker / APP 的信令控制面已扩展 `lan_url`，能自动把局域网地址发送到 Worker 网页端并触发跳转；APP 端已自动启动服务 / 自动建房，Worker 网页端已自动验证 8 位房间码并连接。
   - DataChannel 文件协议 alpha 已完成 JSON + Base64 文本分片、ACK / error、APP 收件箱写盘和 Worker 页面发送 UI。
   - 下一步不是继续补信令，而是真机验证端到端文件传输、补 Native 二进制 chunk，并压测 50MB 级文件。

## 二、评估依据

本次修订不是空想设计，结论基于以下四类事实：

### 2.1 仓库现状

当前仓库中已经存在以下与“传书”直接相关的可复用基础：

1. **现有导入能力已较完整**
   - `entry/src/main/ets/pages/DownloadSyncPage.ets`
   - 该页面已经识别并导入：
     - 漫画压缩包：`zip/cbz/rar/cbr/7z/tar/gz/tgz/bz2/xz/lzma`
     - 电子书：`epub/mobi/azw/azw3`
     - `pdf`
     - `txt`

2. **现有网络扫描能力已存在，但用途不是浏览器传书**
   - `entry/src/main/ets/Framework/Network/NetworkScannerAdapter.ets`
   - `entry/src/main/ets/pages/NetworkFolderPage.ets`
   - 当前实现针对的是 `WebDAV / FTP / FTPS / SFTP / SMB` 这类网络文件夹接入与扫描，不等于已有“网页对 APP 传书”的服务端能力。

3. **现有后台长时任务基础已存在**
   - `entry/src/main/module.json5`
   - `entry/src/main/ets/Framework/Task/BackgroundTaskHelper.ets`
   - 仓库已声明并实际使用 `dataTransfer` 背景模式，也已申请：
     - `ohos.permission.INTERNET`
     - `ohos.permission.GET_NETWORK_INFO`
     - `ohos.permission.KEEP_BACKGROUND_RUNNING`

4. **现有 Cloudflare Worker 已有控制面工程骨架**
   - `docs/cloudflare-worker.md`
   - `cloudflare/manxia-worker/`
   - `entry/src/main/module.json5`
   - 当前仓库已补上 Worker 工程骨架、`wrangler` 配置、Durable Object 信令和 `/transfer` 控制面入口。
   - 它承担 App Linking、深链落地页、传书帮助入口和高级阶段信令协调，不承担局域网发现或上传中继。

### 2.2 本机 HarmonyOS SDK 实际能力

按 `AGENTS.md` 规则，本次优先核对了本机 SDK：

- `F:\HarmonyOS\SDK\23\ets\api\@ohos.net.socket.d.ts`
- `F:\HarmonyOS\SDK\23\ets\api\@ohos.net.webSocket.d.ts`
- `F:\HarmonyOS\SDK\23\ets\api\@ohos.net.http.d.ts`
- `F:\HarmonyOS\SDK\23\ets\api\@ohos.backgroundTaskManager.d.ts`

核对结果：

1. **存在本地 TCP 服务端能力**
   - `constructTCPSocketServerInstance()`
   - `TCPSocketServer.listen(...)`

2. **存在本地 WebSocket 服务端能力**
   - `createWebSocketServer()`
   - `WebSocketServer.start(...)`
   - `WebSocketServer.on('messageReceive', ...)`

3. **存在 HTTP 客户端能力**
   - `createHttp()`
   - 但 SDK 没有提供同级别的现成 ArkTS HTTP Server 封装，需要基于 Socket 自行实现轻量 HTTP 服务。

4. **存在后台长任务能力**
   - `startBackgroundRunning(...)`
   - 可用于 `dataTransfer` 场景。

5. **未在当前 SDK API 声明中检索到可直接采用的原生 WebRTC 能力**
   - 未检索到 `WebRTCKit`
   - 未检索到 `RTCPeerConnection`
   - 未检索到 `RTCDataChannel`

因此，在当前项目基线下：

> **“本地 TCP / WebSocket 服务”是 SDK 已确认能力；“原生 WebRTC 主链路”不是当前阶段可以直接当成已确认能力使用的前提。**

补充核对：

1. **Web 组件桥接能力已在 SDK 声明中存在**
   - `javaScriptProxy(...)`
   - `WebviewController.registerJavaScriptProxy(...)`
   - `WebviewController.runJavaScript(...)`
   - `WebviewController.createWebMessagePorts(...)`
   - `WebMessagePort.postMessageEvent(...)`

2. **官方声明也提醒了安全边界**
   - `registerJavaScriptProxy` 应与可信 Web 组件配合使用。
   - 注册的 JavaScriptProxy 需要在不再使用时删除，避免泄漏。
   - `javaScriptProxy` / `registerJavaScriptProxy` 支持按 URL 权限限制可访问页面。

因此，新的高级阶段判断应改为：

> **ArkTS 原生 WebRTC 不作为依赖；WebRTC 运行时放到受控 Web 页面中，ArkTS 通过 Web 组件桥接接收状态、元数据和文件片段，这是当前更现实的 WebRTC 落地方式。**

### 2.3 浏览器现实约束

现代浏览器对“公网 HTTPS 页面访问局域网本地服务”的限制明显强于旧时代设想，主要问题包括：

1. **Mixed Content**
   - `https://manxia.top` 页面直接访问 `http://192.168.x.x:port` 并不可靠。

2. **Private Network Access / Local Network Access**
   - 浏览器对从公网页面访问本地网段资源的限制越来越严格。
   - 即使部分版本可弹权限提示，也不应把它当作产品级稳定方案。

3. **WebSocket 也受安全上下文影响**
   - `https://` 页面连接 `ws://` 本地服务存在兼容性和策略风险。
   - 若改成 `wss://`，本地服务端证书管理复杂度会大幅上升。

因此：

> **“在 manxia.top 页面里扫描 192.168.x.x 并直连本地 HTTP / ws 服务”不适合作为 MVP 主方案。**

### 2.4 Cloudflare Worker 现实边界

Cloudflare Worker 可以做：

1. 深链落地页
2. App Linking 验证文件
3. 说明页面
4. 小规模控制面能力
   - 房间信息
   - 一次性令牌
   - 信令协调

Cloudflare Worker 不适合直接承担：

1. 局域网设备扫描
2. 直接访问用户局域网
3. 第一阶段的大文件中继主链路

另外，原报告中把 WebSocket 连接写进 KV 的伪代码不成立。WebSocket 会话应由 Durable Object 或服务端内存持有，不能按普通键值对象存储处理。

## 三、问题重新定义

为了让文档真正支撑开发，必须先把“需求说清楚”。

### 3.1 我们真正要解决的核心问题

对当前漫匣来说，“局域网传书”更准确的 MVP 目标应该是：

> 用户在漫匣 APP 中开启传书服务后，能在同一局域网内通过浏览器把漫画压缩包、电子书、PDF、TXT 文件传到 APP，并由 APP 自动导入。

### 3.2 第一阶段不追求的目标

以下目标不建议纳入第一阶段验收：

1. 访问 `manxia.top/transfer` 后自动发现本地设备
2. 完全零输入、零确认、零配对
3. 基于公网 Worker 的大文件转发
4. WebRTC P2P
5. 跨子网、跨 NAT、跨公网传书

### 3.3 第一阶段允许的用户动作

以下动作在 MVP 中是可接受的：

1. 在 APP 内手动开启“局域网传书”
2. 查看并复制本地地址
3. 在浏览器手动输入本地地址
4. 输入 6 位配对码
5. 在 APP 端确认接收

只要交互清晰，这些动作是远比“假自动化但不稳定”更合适的产品取舍。

### 4.2 总体评估

如果把目标改成：

> “APP 开本地服务，浏览器直连 APP 局域网地址上传文件，APP 自动导入”

那么项目是**明确可做**的。

如果坚持目标不变：

> “用户只访问 `manxia.top/transfer`，网页自动扫描局域网并连上漫匣”

那么项目会卡在浏览器安全策略和连接稳定性上，难以成为可靠产品。

## 五、推荐架构

## 5.1 第一阶段推荐架构：局域网本地直连

### 架构说明

第一阶段推荐使用：

**APP 本地 HTTP 服务 + 可选本地 WebSocket 状态通道 + 手动地址 / 二维码辅助**

```text
┌─────────────────────────────────────────────┐
│                 漫匣 APP                    │
│                                             │
│  1. 开启局域网传书                           │
│  2. 启动本地服务                             │
│     - HTTP: 提供上传页面与上传接口           │
│     - WS:   提供进度与状态推送（可选）       │
│  3. 显示本地地址、端口、配对码、二维码        │
│  4. 接收文件后复用现有导入链路               │

                    ▲

```

### 关键原则

1. **数据平面走局域网，不走 Cloudflare**
2. **页面入口优先走本地地址，不走 manxia.top 代理**
3. **控制面可以很轻，传输面必须稳定**
4. **先做能稳定收书，再谈自动发现**

## 5.2 `manxia.top` 在第一阶段的定位

第一阶段建议把 `manxia.top` 定位为：

1. 深链拉起入口
2. 帮助说明页
3. 传书功能介绍页
4. 后续版本升级入口

不建议把 `manxia.top` 第一阶段定位为：

1. 局域网发现器
2. 文件上传中继
3. WebRTC 信令核心

### 推荐表现形式

`https://manxia.top/transfer` 可以做成：

1. 介绍如何在 APP 内开启传书
2. 提供“打开漫匣”按钮
3. 展示三种连接方式：
   - 手动输入局域网地址
   - 查看 APP 显示的二维码
   - 复制本地地址到浏览器打开

它是**入口和说明页**，不是第一阶段实际数据通道。

## 七、安全设计建议

第一阶段安全目标不是“零信任企业级”，而是“局域网可用且不会裸奔”。

## 7.1 必做项

1. 服务默认关闭
2. 用户手动开启服务
3. 使用 6 位或 8 位一次性配对码
4. 配对成功后发放短期 token
5. token 过期自动失效
6. 服务空闲自动关闭
7. 限制可上传后缀和 MIME 类型
8. 限制单文件大小和总会话大小
9. 文件名做清洗，禁止路径穿越
10. 记录关键操作日志

## 7.2 建议项

1. 首次连接时在 APP 上显示客户端名称和 IP
2. 可选“需要点击确认才接收”
3. 绑定同一局域网会话
4. 同时上传连接数限制
5. 导入失败后保留错误原因和清理策略

## 7.3 不建议第一阶段做的复杂项

1. 自建 TLS 证书本地 `https/wss`
2. 端到端自定义加密层
3. 基于 Cloudflare 的公网 relay 加密隧道

## 九、WebRTC / Native RTC 路线的重新定位

原报告最大的问题不是“WebRTC 完全不可能”，而是**把它放错了阶段和承载层**。

### 9.1 当前不推荐的原因

1. 当前本机 SDK 与仓库里没有现成 WebRTC 落地依据
2. 第一阶段真正的需求是“稳定收书”，不是“炫技式 P2P”
3. 即使 WebRTC 成立，浏览器入口、信令、回退、失败处理仍然复杂
4. 大文件传输时，产品首要问题是稳定与可恢复，而不是协议先进性

这里的“不推荐”，指的是**不推荐把 WebRTC / Native RTC 当作 Phase 1 主链路**，不再等同于“WebRTC 不能做”。

### 9.2 Native RTC 为什么成为优先路线

相比 Web 组件嵌入 WebRTC 页面，Native RTC 路线更适合漫匣当前工程的原因：

1. 文件数据在 ArkTS / Native 边界内流动，避免 ArkWeb 页面与 ArkTS 之间大量 `ArrayBuffer` / Base64 转换。
2. 后续可直接把 DataChannel 收到的分片写入收件箱临时文件，减少 Web 页面桥接层状态复杂度。
3. `TransferSignalClientService.ets` 已经负责 Worker WebSocket 信令，不需要在 Web 页面中再维护一套 Host 信令客户端。
4. `libdatachannel` 比 Google libwebrtc 更轻，更符合“只需要 DataChannel，不需要音视频”的需求。

当前已完成真实后端接入和文件协议 alpha，不等于大文件生产级闭环已经完成：

1. Native 模块已注册 `transfer_rtc_native`。
2. ArkTS 已能 import `libtransfer_rtc_native.so` 并读取能力。
3. Native C++ 已使用 `rtc::PeerConnection` / `rtc::DataChannel` 替换 stub。
4. `createOffer / createAnswer / setRemoteDescription / addIceCandidate / sendText / pollEvents` 已走真实后端代码路径。
5. `TransferRtcFileReceiverService.ets` 已可把 `mx-transfer-file/0.1` 文本分片写入收件箱并返回 ACK。
6. 剩余是真机跨设备联调、50MB 级大文件、二进制 chunk 和失败回退。

### 9.3 Web 组件 DataChannel 方案为什么仍保留

通过 `Web` 组件嵌入 WebRTC 页面后，WebRTC 逻辑完全运行在 ArkWeb 的 JavaScript 环境中：

1. `RTCPeerConnection`、`RTCDataChannel`、`WebSocket` 等标准 Web API 由页面负责。
2. APP 端 ArkTS 不直接调用 WebRTC API，只负责加载页面、注入桥接对象、展示状态、落盘和导入。
3. 现有 Worker 继续只转发 SDP / ICE / 房间状态，不承载文件数据。
4. 文件数据通过 DataChannel P2P 传输；接收端 Web 页面将分片通过桥接交给 ArkTS。

这条路线规避了“ArkTS 没有原生 WebRTC API”的问题，也能复用已经落地的 Worker 房间码控制面。

### 9.4 WebRTC 适合放到什么阶段

只有在下面条件满足后，才建议重新评估：

1. 局域网本地直连 MVP 已完成并稳定。
2. 目标真机确认 ArkWeb 支持 `RTCPeerConnection` 和 `RTCDataChannel`。
3. 已明确 Web 页面加载形态：优先 `$rawfile(...)`，不满足安全上下文时改用受控 HTTPS 页面。
4. 已确定 JS 到 ArkTS 的分片桥接方式：优先 `WebMessagePort + ArrayBuffer`，回退 `javaScriptProxy + 小块 Base64`。
5. 已接受 STUN/TURN、NAT 失败回退、断线恢复和大文件背压带来的额外复杂度。

### 9.5 不建议默认申请摄像头 / 麦克风权限

DataChannel 本身不需要音视频采集。新的 WebRTC 传书方案应默认只依赖网络能力：

1. `ohos.permission.INTERNET` 已存在。
2. 不默认新增 `CAMERA` / `MICROPHONE`，避免用户误解传书功能会采集音视频。
3. Web 组件 `onPermissionRequest` 中如收到摄像头或麦克风请求，默认拒绝；只有未来明确引入音视频能力时再单独申请并解释。
4. 真机验证如果发现 ArkWeb 在纯 DataChannel 建连时仍异常请求音视频权限，再把它作为兼容性问题单独处理，而不是提前扩大权限面。

## 十、为什么不推荐“网页自动扫描局域网设备”

这是最容易在立项阶段误判、开发阶段卡死、上线阶段不稳定的部分。

### 10.1 不推荐原因

1. 浏览器安全策略不稳定
2. HTTPS 页面对本地 HTTP / ws 访问受限
3. 扫描整个网段会带来性能、权限、误报、用户认知问题
4. 不同浏览器、不同平台、不同版本行为可能不一致

### 10.2 结论

> “自动发现”只能作为后续增强方向，不能作为当前版本的基础前提。

如果后续确实需要增强体验，优先顺序应为：

1. APP 直接展示本地地址
2. APP 生成二维码
3. 研究是否支持局域网服务名
4. 最后才考虑网页自动发现

1. 在真机上验证 `libdatachannel` 后端能力检测、offer / answer / candidate 交换和 DataChannel open。
2. 定义并实现 `mx-transfer-file/0.1` 文件分片协议。
3. DataChannel 收到文件片段后复用 `TransferUploadStoreService.ets` 写盘与导入。
4. 浏览器 `/transfer` 在当前 RTC 测试端基础上补文件选择、分片发送、ACK / 背压控制。
5. P2P 不通时明确回退局域网 HTTP 直连，必要时再评估 TURN / relay。

### 信令协议

沿用当前 Worker 消息外壳：

```json
{
  "type": "offer",
  "targetRole": "peer",
  "targetClientId": "",
  "payload": "{\"type\":\"offer\",\"sdp\":\"...\"}",
  "requestId": "optional-client-request-id"
}
```

约束：

1. `payload` 只放 SDP / ICE JSON 字符串。
2. 单条信令继续遵守 Worker 64KB 上限。
3. 房间仍然区分 `host` / `peer`。
4. `hostToken` 只保存在 APP 端，不泄露给浏览器 peer。

### DataChannel 文件协议

建议通道名：`mx-transfer-file/0.1`

当前 alpha 状态：

1. Worker `/transfer` 浏览器端已经按该协议发送文件。
2. APP 端 `TransferRtcFileReceiverService.ets` 已按片写入 `TransferUploadStoreService` 收件箱。
3. 由于 Native NAPI 当前只暴露 `sendText` / 文本事件，`file_chunk` 暂用 JSON + Base64 文本承载；协议结构已为后续二进制 `ArrayBuffer` chunk 留好边界。

控制消息使用 JSON 文本：

```json
{
  "type": "file_start",
  "protocol": "mx-transfer-file/0.1",
  "transferId": "file_001",
  "fileName": "example.cbz",
  "contentType": "application/octet-stream",
  "size": 12345678,
  "chunkSize": 49152,
  "chunkCount": 252,
  "clientName": "Browser RTC"
}
```

文件片段目标形态优先使用二进制 `ArrayBuffer`。当前 alpha 使用文本回退：

```json
{
  "type": "file_chunk",
  "protocol": "mx-transfer-file/0.1",
  "transferId": "file_001",
  "chunkIndex": 0,
  "offset": 0,
  "byteLength": 49152,
  "data": "base64..."
}
```

结束消息：

```json
{
  "type": "file_end",
  "protocol": "mx-transfer-file/0.1",
  "transferId": "file_001"
}
```

APP 回 ACK：

```json
{
  "type": "ack",
  "protocol": "mx-transfer-file/0.1",
  "transferId": "file_001",
  "status": "chunk",
  "receivedBytes": 49152,
  "nextChunkIndex": 1
}
```

背压要求：

1. 浏览器发送端监听 `RTCDataChannel.bufferedAmount`，超过阈值暂停读取文件。
2. 浏览器发送端等待 APP 对每片返回 `ack` 后再继续下一片。
3. ArkTS 写盘失败时立即回传 `error`，并清理收件箱临时文件。

### 第一轮真机 PoC 验收

1. APP Web 组件页面输出：
   - `window.isSecureContext`
   - `typeof RTCPeerConnection`
   - `typeof RTCDataChannel`
   - `typeof WebSocket`
2. APP 创建 Worker 房间后，浏览器 peer 能完成 offer / answer / candidate 交换。
3. DataChannel 能打开并互发文本 ping。
4. 传输一个 1MB 测试文件，APP 能落入收件箱。
5. 传输一个 50MB 文件，验证背压、进度、失败清理和继续导入。
6. P2P 失败时能明确提示回退局域网直连。

## 十二、建议的验收标准

## 12.1 功能验收

必须满足：

1. APP 开启服务后能显示局域网地址
2. 浏览器访问本地地址能看到上传页面
3. 配对成功后可上传文件
4. 上传完成后 APP 自动导入
5. 支持以下文件类型：
   - 漫画压缩包
   - 电子书
   - PDF
   - TXT
6. APP 关闭服务后地址失效

## 12.2 稳定性验收

建议至少覆盖：

1. 10MB 文件
2. 100MB 文件
3. 500MB 文件
4. Wi-Fi 稳定场景
5. 浏览器刷新场景
6. APP 切后台场景
7. 传输中断场景

## 12.3 安全验收

必须满足：

1. 未配对不能上传
2. token 过期后不能继续上传
3. 非支持文件类型拒绝导入
4. 文件名不能造成路径穿越
5. 服务关闭后不再接受连接

## 十三、后续开发建议

为了减少返工，建议按下面顺序推进：

1. **先做技术验证**
   - 验证本地 HTTP 服务最小可用实现
   - 验证浏览器访问本地地址是否稳定
   - 验证上传后接入现有导入链路

2. **再做正式页面**
   - 传书设置项
   - 传书主页
   - 上传状态页

3. **最后再考虑 Cloudflare 入口页**
   - 不要一开始就做公网入口与信令体系

## 十四、最终建议

### 14.1 立项建议

建议正式按以下版本目标立项：

> **漫匣局域网传书 MVP：APP 开启本地传输服务，浏览器通过局域网地址直连 APP 上传文件，APP 自动导入。**

### 14.2 不建议立项时写进承诺的内容

以下内容不要写进第一阶段对外承诺：

1. 自动扫描局域网设备
2. WebRTC P2P
3. 访问 `manxia.top` 即自动连上 APP
4. 跨公网传书

### 14.3 推荐路线总结

**当前最靠谱、最贴合你们仓库现状、最能支撑后续开发工作的路线是：**

1. 复用现有导入链路
2. 新增本地轻量服务端
3. 浏览器直连局域网地址
4. 用配对码与短期 token 保证基本安全
5. `manxia.top` 只做入口与说明，不做第一阶段数据通道
